# Threat model (draft)

**Status:** draft for architecture. Must be reviewed before any real patient data is stored (Phase 8).

Method: pragmatic STRIDE-style, assets-first. Not a substitute for a professional security assessment.

## 1. Assets

| Asset | Sensitivity |
| --- | --- |
| Patient demographics and contacts | High |
| Clinical notes, assessments, measurements | Very high |
| Rehabilitation plans and goals | Very high |
| Body annotations / heatmap source data | Very high |
| Documents (IDs, referrals, imaging reports) | Very high |
| Staff identity, roles, membership | High |
| Audit logs | High (integrity) |
| Object-storage credentials and signed URLs | High |
| Session tokens / IdP tokens | Critical |
| Anatomical model files | Low (IP/license), no PHI |
| Availability of scheduling | Medium (operations) |

## 2. Actors

| Actor | Trust |
| --- | --- |
| Rehabilitation specialist | Authenticated staff; not fully trusted (least privilege, audit) |
| Receptionist | Authenticated staff; no clinical read by default |
| Organization admin | Staff management; not automatic full chart |
| System admin | Infrastructure; PHI break-glass is a risk |
| Malicious or compromised staff (insider) | Abuses legitimate access |
| External attacker | Network, stolen laptop, phishing |
| Patient / public | **No accounts**; still a threat via exposed URLs, stolen files |
| Third-party IdP admin | Can mint sessions if IdP is compromised |
| Backup operator | Can read snapshots if backups unencrypted |

## 3. Trust boundaries

1. Browser ↔ Next.js (cookie, XSS, CSRF)
2. Next.js ↔ NestJS (SSRFable if web can be tricked to call arbitrary URLs)
3. NestJS ↔ PostgreSQL
4. NestJS ↔ Redis
5. NestJS ↔ MinIO/S3
6. NestJS ↔ Keycloak (JWKS, token)
7. Operators ↔ production secrets / backups
8. CI ↔ repository (supply chain)

## 4. Entry points

- Staff UI routes and BFF
- `GET/POST /api/v1/*`
- OpenAPI in non-production only (disable or protect in production)
- Object-storage signed URLs
- Keycloak login, password recovery, MFA
- Health endpoints (no PHI)
- Webhooks (none in v1; future risk)

## 5. Abuse cases and mitigations

| ID | Abuse case | STRIDE | Mitigation (target) |
| --- | --- | --- | --- |
| T1 | Receptionist reads clinical notes by UUID | Elevation / info disclosure | Permission + tests; no IDOR; DTO projection |
| T2 | User sets `organizationId` of another clinic | Horizontal privilege | Ignore client org; bind to membership |
| T3 | Stolen session cookie | Spoofing | httpOnly Secure cookies, short TTL, refresh rotation, IdP session logout, staff disable invalidates |
| T4 | XSS steals data | XSS | CSP, React encoding, no `dangerouslySetInnerHTML` for clinical text without sanitizer |
| T5 | CSRF on BFF | CSRF | Staff API is Bearer from the BFF, not browser cookies on NestJS. Auth.js cookies are httpOnly + SameSite=Lax. Phase 2 mutations are Next.js Server Actions (origin-checked). A future cookie BFF proxy must verify Origin. HttpOnly does not prevent CSRF by itself. |
| T6 | Malicious upload (malware, SVG XSS, polyglot) | Tampering | MIME allow-list, size cap, scan hook, no public bucket, Content-Disposition attachment |
| T7 | Public MinIO bucket | Info disclosure | Private buckets, no wildcard ACL, signed URLs only |
| T8 | Path traversal / SSRF via storage keys or webhooks | SSRF | Key prefix generated by server; deny user-controlled URLs |
| T9 | SQL injection | Tampering | Prisma parameterized queries only |
| T10 | Brute force login | Spoofing | Keycloak brute-force + MFA capability; API rate limits |
| T11 | Insider bulk export | Info disclosure | Audit, rate limit list endpoints, no unbounded export in v1, `audit.read` restricted |
| T12 | Audit log tampering | Repudiation | Append-only table, no update API, DB role without DELETE, later WORM/SIEM |
| T13 | Tokens in logs | Info disclosure | Structured logs redaction; never log Authorization or bodies |
| T14 | Insecure backups | Info disclosure | Encrypted backups, access control, restore tests (Phase 8) |
| T15 | Dependency compromise | Tampering | Lockfile, CI audit, pinned actions |
| T16 | 3D model from untrusted URL | XSS / SSRF | Models only from our storage keys |
| T17 | Confused deputy: specialist A edits patient of specialist B inappropriately | Elevation | Care-relationship policy (tighten after v1 temporary org-wide specialist access) |
| T18 | Replay / concurrent overwrite of patient or rehab plan | Tampering | Optimistic `version` → 409 (ADR-008 for Patient) |
| T19 | Keycloak misconfiguration (public client secrets) | Spoofing | Confidential vs public client design in ADR-003; realm review |
| T20 | Health/OpenAPI leak of config | Info disclosure | Health without dependency secrets; Swagger off in production by default |
| T21 | Cross-org patient UUID probe | Info disclosure | Scoped find + 404; no AuthorizationProbe fixture in production |
| T22 | Audit metadata over-collection | Info disclosure | Controlled changedFields only; no full patient JSON in audit |
| T23 | Silent duplicate patient merge | Tampering / integrity | Non-blocking warnings only; no auto-merge (Q10) |
| T24 | Double-book same practitioner slot | Integrity / availability | PostgreSQL GiST exclusion on practitioner time range; API 409 `APPOINTMENT_TIME_CONFLICT` (ADR-010) |
| T25 | Schedule archived/completed patient | Policy bypass | `PATIENT_NOT_SCHEDULABLE` on create; org-scoped patient lookup |
| T26 | Receptionist starts clinical encounter | Elevation | `encounter.start` / `encounter.complete` specialist-only; authorization tests |
| T27 | Receptionist or admin reads assessment values/summary | Elevation / info disclosure | Separate assessment/measurement permissions; clinical section omitted from UI; backend remains authoritative |
| T28 | Browser impersonates another practitioner | Spoofing | Resolve active Practitioner by authenticated `userId` + organization; no practitioner field in create DTO |
| T29 | Cross-org assessment/template/history UUID probing | IDOR / info disclosure | Organization-scoped repositories and concealment as 404 |
| T30 | Stale tab overwrites clinical measurements | Tampering | Assessment version compare-and-swap; transactional whole-draft save; 409 on conflict |
| T31 | Clinical values leak through request/audit logs | Info disclosure | Redact summary, measurements, and void reason; audit only IDs, transitions, field names, definition codes |
| T32 | Receptionist/admin reads a plan or prescription by guessed UUID | Elevation / info disclosure | Separate plan/goal/prescription permissions; backend projection guard; clinical sections omitted from UI |
| T33 | Receptionist/admin reads or mutates body annotations by guessed UUID | Elevation / info disclosure | Separate body-annotation permissions, org-scoped lookups, clinical UI hidden, authorization tests |
| T34 | Client forges mesh UUID/name or mismatched structure/version anchor | Tampering | Accept only reviewed mapping ID + exact version + stable key + primitive; validate barycentric values server-side and in PostgreSQL |
| T35 | Model replacement silently moves historical markers | Integrity | Immutable checksum/version/storage key; no cross-version reprojection; retain textual record |
| T36 | Public model bucket or leaked signed URL credentials | Information disclosure | Private bucket, five-minute GET signatures, server-only S3 credentials, no signed query-string logging |
| T37 | Annotation narrative leaks to generic audit/logs | Information disclosure | Audit metadata allow-list; logger redacts `note` and `anchor`; no body-map response logging |
| T33 | Active plan history is silently overwritten | Tampering / repudiation | Immutable published revisions; one explicit draft; transactional publish and current pointer |
| T34 | Cross-org baseline or exercise is attached to a plan | Horizontal privilege / integrity | Org-scoped reference validation; shared exercises only when `organizationId IS NULL`; conceal foreign IDs |
| T35 | Two clinicians overwrite the same draft | Tampering | Plan version compare-and-swap; transaction rollback and safe 409 |
| T36 | Clinical plan content enters generic audit or HTTP logs | Info disclosure | Request-body redaction; audit only entity IDs, revision numbers, changed child IDs, and transitions |
| T27 | Concurrent appointment reschedule overwrite | Tampering | Optimistic `version` on Appointment → 409 (same pattern as Patient) |
| T28 | Timezone confusion (local vs clinic) | Integrity / ops | Store `timestamptz`; display via org/location IANA timezone in UI |
| T38 | Receptionist/admin infers clinical progress or downloads a report by UUID | Elevation / disclosure | Separate specialist-only permissions, org-scoped lookup, UI omission, authorization tests |
| T39 | Signed report URL is copied or logged | Disclosure | Five-minute expiry, attachment disposition, private bucket, no URL logging; recipient remains responsible during validity |
| T40 | Report narrative or measurements enter logs/audit | Disclosure | Logger redacts professional summary; audit stores identifiers/counts only; DTO excludes snapshot metadata/storage key |
| T41 | Source data changes after export and report becomes ambiguous | Integrity / repudiation | Immutable PDF, template version, source IDs/versions/timestamps, author and generation time; explicit void retains original |
| T42 | Unbounded longitudinal query enables bulk PHI scraping | Disclosure / availability | 90-day default, ten-year cap, page-size cap, dedicated endpoints, authenticated rate limit |

## 6. Residual risks (accepted until Phase 9 hardening)

- No penetration test, load test, or formal accessibility/browser matrix yet
- Care-relationship is temporarily coarse (same-org specialist)
- Malware scanning is an **integration point**, not implemented
- Backup encryption and report-object restore are not verified
- No SIEM shipping or signed-URL revocation mechanism
- Ukrainian patient name search may miss variants under default Postgres indexes
- Duplicate-warning UI may lag behind detection architecture
- Practitioner calendar read is org-wide in Phase 4 (future per-practitioner scoping)
- Room double-booking not blocked at DB layer yet (Q11)

## 7. ASVS alignment (baseline intent)

Track OWASP ASVS v4.0.3 / v5 categories: authentication (IdP), session, access control, validation, files, stored cryptography (TLS + disk + backups), logging, configuration. A full checklist is a Phase 8 deliverable, not claimed complete now.
